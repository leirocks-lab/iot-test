# Spec 管理约定

## 功能粒度与编号

- 可独立验收的业务能力一份 spec；页面、API、状态不能自动变成独立功能。
- 功能 ID：RF-0001，按已分配最大值继续递增；永不复用或随目录改名改变。
- 验收 ID：RF-0001-AC-001，追加编号；删除项保留历史，不重新分配给其他行为。
- 原始条目：REQ-001 对应 Excel 原序号 1；同时记录工作表及物理行号。
- 变更 ID：CHG-YYYYMMDD-NNN，同一天从 001 递增。
- 目录和文件使用中文，层级为业务域/功能组/功能；无组时允许业务域/功能。扩展名保持 .md、.yaml、.mjs 等标准格式。
- 变更目录使用 `迭代变更/变更-YYYYMMDD-NNN/`，正文记录稳定 CHG 编号；发布目录使用 `发布基线/应用-<版本>/`。

## 元数据

功能规范.md 的 YAML frontmatter 是功能信息唯一维护入口。id、title、domain、version、spec_status、delivery_status、owners、updated_at、dependencies、sources 必填。group 无组时设为 null。

本项目使用 domain_title、group_title 对应中文业务域和功能组目录；domain、group 保留稳定机器标识。priority 保留范围优先级，requirements 记录唯一主归属条目，apis 记录范围内接口编号，conflicts 关联待确认记录。这些数组为空时写 []。

owners 来自 Excel；后续调整要有变更依据。updated_at 是规范修改日期，不是原始资料版本。sources 每项必须有已登记资料 ID 与可定位章节、工作表/行、页码/节点或 UI 文件路径。

## 规范与交付状态

规范：draft（待评审）、approved（已确认可开发目标）、deprecated（停用，保留 ID 与历史）。交付：unplanned、planned、in_progress、verified、released。规范可以已批准而实现仍未交付。

- approved 前解决关联 open 冲突，并在变更包记录确认依据。
- verified 前逐条记录 AC 验收证据；不能把文档校验通过作为业务验收。
- released 需要真实发布基线；没有发布不建立虚假 manifest。
- deprecated 仍保留历史需求归属，不能靠删除 spec 隐藏未覆盖条目。

## 版本

初次归档 0.1.0；经业务和接口确认进入 1.0.0。MAJOR 为不兼容业务/接口/验收变化，MINOR 为兼容新增场景，PATCH 为不改变行为的文字与引用修正。

规范变更更新版本、日期与版本记录，关联 CHG。目录、文件和引用的中文命名迁移不改变业务行为，按 PATCH 记录为 0.1.1。交付状态或负责人变化记录日期与变更说明，不因状态变化强制改变业务规范版本。原始 Word V1.4 是来源版本，不是功能版本。

完整历史由 Git 保存，不建立 spec-v1/spec-v2 副本。发布 manifest 记录已提交的完整 40 位规范 SHA；其功能路径和版本必须与该提交一致。

## 范围与来源变更

来源资料/范围快照.yaml 是 Excel 内容的可检索快照，不是新增范围的授权入口。新增功能须先获得用户确认的范围变更，然后更新原始范围依据、资料登记、快照、spec 归属及覆盖报告。

来源哈希变化时先重读差异、确认范围与契约影响，再更新登记；不能为了通过检查只替换 hash。UI 文件目录哈希按排序后的 UTF-8「仓库相对路径 + NUL + 文件 SHA-256 + LF」计算，不包含绝对路径。

普通文字引用不会在索引中成为新增功能。范围条目必须只有一个主归属，跨功能共享能力通过 dependencies 关联，不能循环依赖。

## 工具与发布检查

运行 pnpm specs:index 生成功能索引及范围覆盖，pnpm specs:check 检查元数据、范围覆盖、负责人、API 引用、验收 ID、版本记录、依赖、链接、来源哈希和实际发布清单。pnpm specs:test 验证工具行为。维护命令保留已有名称，对应脚本位于 `sdd/维护工具/`。

发布清单校验从 spec_git_commit 指定提交读取规范，而非当前文件。SPECS_GIT 可设置 Git 可执行文件路径；正常环境默认 git。发布须先提交已批准且 verified/released 的规范，再创建引用该提交的 manifest，避免自引用 SHA。
