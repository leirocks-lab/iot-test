# CHG-20261022-002 0822配网流程核查

状态：资料核查；不是已批准功能规范或板级验收。仅讨论已选 `AT+SOFTSTART=5`、BLE UUID `0x0822` 路线。旧版 `0x0922` JSON 分包不能直接套用。

后续结论：用户已确认 App 在校验固件 `0x0F` 后发送 `0x8F`，DATA 为零长度；固件对此帧校验 CRC。下文提到的“新版 `0x8F` DATA 缺失”是确认前的核查快照。双路线真实接入 profile 现已注册，空绑定码经 `0x04` 发送，无码时改由 HOME-01 唯一 MAC 匹配确认；这些行为仍需板级与云端实测。

## 参与方

| 参与方 | 配网职责 |
| --- | --- |
| MCU | 预先用 `AT+MODELID=<series>,<model>` 设置产品身份，并用 `AT+SOFTSTART=5` 让模组进入新版 BLE 广播模式；后续接收模组的串口事件。 |
| App | 从广播解析 MAC/型号并匹配产品；读取当前 Wi-Fi，向业务 API 取得四个配网 URL；连接 BLE，完成 `0x00/0x0F/0x8F` 校验，逐项发送十个参数并检查 ACK；显示模组状态，最后向业务云确认当前账号绑定结果。 |
| Wi-Fi/BLE 模组 | 接收、校验及保存参数；收齐后连接路由器，依次完成云端认证 C、激活 B、绑定 D、证书 E、MQTT F，通过 BLE Notify 上报状态；不把设备私钥交给 App。 |
| 业务云 | 给 App 提供产品与 PAIR-04 配网地址；响应模组的设备侧认证/激活/绑定/证书请求；提供 PAIR-05/PAIR-06 或 HOME-01 的账号绑定结果。具体设备侧 HTTP method/body/response 缺失，不能从 App OpenAPI 推造。 |

## 消息顺序

1. MCU 已设置正确系列/型号后触发 `SOFTSTART=5`。模组广播 `0x0822`；App 从厂商广播数据读取 MAC 和型号，使用 `0xAAB1` Write、`0xAAB2` Notify。BLE Key 来源为小写无冒号 MAC 加型号前4字符。
2. App 校验产品及当前 Wi-Fi，调用 PAIR-04 `GET /api/app/device/connection` 取得 `certificationURL`、`activationURL`、`bindingURL`、`otaURL`。这些是给模组后续访问云端的地址，App 不是靠自己调用四个 URL 完成设备入云。
3. App 发 `0x00` 身份摘要，模组回 `0x80`，再发 `0x0F` 工厂摘要；App 核对后发 `0x8F` 确认。0822帧由 `A5 5A`、长度、AES-CTR 加密的 CMD+DATA、明文载荷 CRC8 组成。新版 `0x8F` DATA 未给，旧V1.1 `ok` 不能自动视为新版答案。
4. App 按顺序发 `0x01` SSID、`0x02` 密码、`0x03` 用户 Token、`0x04` 绑定码、`0x05` 产品ID、`0x06` 型号、`0x07` 证书URL、`0x08` 激活URL、`0x09` 绑定URL、`0x0A` OTA URL；每项等待对应 `0x81`～`0x8A` ACK。`0x84` 只说明模组接受该参数，不代表云端已绑定。
5. README 记录 `get_info_flag==12` 后模组才开始 Wi-Fi，12项为 `0x00`、`0x8F` 与十个参数。A1→A0 是连路由过程，A2/A3/A4 是错误。模组随后依次回报 C（认证）、B（激活）、D（绑定）、E（证书）、F（MQTT连接）阶段。
6. D1=模组正在绑定，D0=模组报告绑定成功；D2～D5、D8～DB 是模组报告的绑定阶段失败。新版 README 仅明确 D3 对应云端 code 11000、D4 对应 16003，未解释两 code 业务含义；旧V1.1 将 D3 记为“重复”、D4 记为“DeviceID”，但不应据此给新版错误定性。测试镜像含两个 code 对应的日志字符串，仍缺实板和云端响应验证。
7. F0 表示模组 MQTT 连接成功，不等于 App 已核实当前用户与设备的绑定关系。现有二期 App 路径随后用 bindCode 调 PAIR-05 轮询，取得 deviceID、userID、bindingRole 才进入添加结果。云端 PAIR-06 一期允许省略 bindCode 请求体，但要先有 deviceId；不能把两者混为同一设备侧绑定 API。

## 绑定码可选的独立问题

- App 本地不应把绑定码缺失直接判作添加失败，这是用户已确认的行为目标。
- README 仍把 `0x04` 算作收齐步骤。测试镜像包含 `bindcode is null!` 等字符串，却不能证明当前板子对空DATA/跳过帧的实际响应。该设备行为需板级测试或固件方说明。
- 模组设备侧 Binding URL 的请求体、无码行为和 D3/D4 云端错误语义未给；PAIR-06 的 body 可选并不能证明该设备侧接口同样可选。
- 无码时 PAIR-05 无法查询。HOME-01 可尝试用返回的设备 MAC 与广播 MAC 匹配，并取得该账号设备 ID/角色；但 OpenAPI 仅要求设备 ID 必返，MAC 可能缺失，未匹配时不能宣称添加成功或绑定失败。
- 当前真实接入 registry 为空，且新版 `0x8F` DATA 缺失；取消绑定码本地门禁本身不足以让真实手机配网完成。
