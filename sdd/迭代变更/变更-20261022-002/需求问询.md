# CHG-20261022-002 需求问询

日期：2026-10-22。范围：RF-0020 真实0822配网中绑定码可选性的用户新决定，以及工厂确认步骤解释。

## 用户实际指令

“WiFi密码输入后点下一步，显示添加失败。绑定码非必填，故不要因缺少就报添加失败。0822工厂确认契约是指什么？用来干嘛的”

随后用户明确补充：“那先按绑定码非必填，遇到问题我再去沟通。0822工厂确认契约是指什么？用来干嘛的”。该指令确认 App 不应将绑定码本身作为必填条件；不等于确认设备接受空0x04、可省略0x04或绑定已经成功。

这明确提出绑定码可选的目标。2026-10-22 用户进一步追问“怎么判断 0822 固件把绑定码列为必收参数”，因此明确纠正先前表述：现有 README 只支持“0x04 被列入收齐流程”的文档推断，不能证明这块板上的固件要求非空绑定码。设备实际行为待核实。

## 已核实事实与来源

- 唯一范围 Excel REQ-054/055：统一配网状态、绑定结果轮询；REQ-051：Wi-Fi密码输入。RF-0020 当前版本1.5.0、draft/in_progress，尚无真实完整验收。
- [新版0822配网说明](<../../../docs/RowanBleNetconfTest/README_BLE配网.md>) §6.2/6.4：0x04 `set_bindcode` 为10个依序参数之一；表中失败/空回包为0x74/0x14；`get_info_flag` 列出 bindcode，计数满12才触发连Wi-Fi。该文档未描述跳过0x04或空值替代的分支，也未明说空值一定不计数。仓库没有对应固件源码和空码实测证据。
- [测试固件二进制](<../../../docs/RowanBleNetconfTest/ble_provision_test_v1.0.0.bin>) 可读字符串包含 `bindcode is null!`（约0xC92C4）、`bindcode null`（约0xC84A8）、`ble send cloud reply with bind fail code=11000/16003`（约0xC87D4/0xC8804）。这支持“该测试镜像存在空码检查及这两种错误分支”，不能证明用户当前板子运行同一镜像，也不能仅凭字符串判断跳过0x04或空DATA时是否计数、云端是否允许无码。
- 已登记部署OpenAPI `GET /app-api/device/bindStatus`（PAIR-05）：`bindCode` 为必填Query，按Redis码查询绑定状态；现有 `src/services/rowan.ts` 与 `src/services/onboarding.ts` 据此轮询。另有 `PUT /app-api/device/{deviceId}/user`（PAIR-06）：`bindCode` 请求体字段可选，说明“一期配网可不带 body”，但必须提供路径 `deviceId`；其同一说明中的错误校验顺序又列了码存在性，仍须真实接口澄清。现有扫描结果仅含MAC和型号，无可直接用于PAIR-06的设备ID。
- README §6.2/6.4：模组先回0x0F工厂摘要，App发0x8F确认；收到校验合格的0x8F才增加配网收齐计数。§6.4将0x8F列入12项。旧固件V1.1曾给0x8F DATA=`ok`，但已选新版README只写`0x8F+...`，当前准确DATA未确认。已有[协议核查](<../变更-20261011-003/接口与协议核查.md>)保留该限制。
- 现有App `deploymentIntegrations` 为空、测试配置未提供 `ROWAN_INTEGRATION_PROFILE`；在 `src/services/onboarding.ts` 真实模式先触发“真实绑定码及0822工厂确认契约尚未配置”，并未发设备凭据。这条错误把两个独立缺口合并，无法准确说明当前原因。

## 决策树与问题

第1轮：设备及云端对缺少绑定码的行为，依赖已核实协议事实。

- Q1：绑定码本身是否作为 App 本地必填？建议否。用户实际回答：2026-10-22“那先按绑定码非必填，遇到问题我再去沟通”，采纳“App不因缺码直接报添加失败”。设备对跳过0x04或发送空值的实际行为仍待核实；PAIR-05要求绑定码，PAIR-06虽可省码却需要deviceId。
- Q2：无码时设备 Wi-Fi 已连接但账号绑定仍无法确认，页面是否进入“绑定待确认”，不显示“添加成功”？建议是，避免把Wi-Fi连接误报为绑定。已提交用户问询，实际回答待记录。
- Q3：能否提供新版0822 0x8F确认帧的准确DATA？已有资料仅有旧版`ok`示例和新版`0x8F+...`；已提交用户问询。此为固件协议事实，不以用户偏好或建议填充。

第2轮：实现路径，依赖Q2和Q3答案及设备/云端契约。待用户回答后记录后续问题、建议与实际回答。

## 待确认与最终共同理解

本包尚未形成共同理解，规范及实现保持待确认。用户已授权修正“缺码就添加失败”的目标，但设备端如何计数和云端如何确认仍需能执行的契约。0x8F步骤解释不构成新DATA确认。

用户随后要求重新梳理 App、模组、云端的实际职责及D组状态；已核对事实和问题见[0822配网流程核查](<0822配网流程核查.md>)。此次只读核查不视为Q2/Q3的回答或最终共同理解确认。

2026-10-22 用户再提供外部《WiFi模组联调 API手册 v1.0》，要求检查三端接口实现程度。手册 SHA-256 `F6D019D237670461B03C1DF8846DE2FFA90A3C076735C03DF1DD1B245D88BE88`；手册自述是固件侧根据现有实现整理的理解，“实际以三方联调为准”。已单独记录[三端接口现状核查](<../../../docs/联调核查/三端接口现状-20261022.md>)。新增事实：新版0822称 `0x04` 缺参数报 `0x14`，设备绑定 POST Body 含 `bind_code`；D3=11000参数错，D4=16003已有户主，D8=404、D9=502；手册同时称旧0922用于用户配网、新0822用于售后配网，但未提供新版0x8F DATA。这强化了无码分支和路线选择的待确认程度，不撤销用户的“App本地绑定码非必填”目标，也不把手册理解直接当作板级验收。

- Q4：当前酒柜普通用户首次添加应使用旧0922还是新0822？用户于2026-10-22明确回答：“两种蓝牙配网都要实现，app需根据设备广播的uuid区分使用哪个进行配网”。不以产品类别或“用户/售后”文案强行选路。

## 2026-10-22 新一轮明确决策

用户原话：“重新澄清 1、两种蓝牙配网都要实现，app需根据设备广播的uuid区分使用哪个进行配网；2、业务无法明确拿到的参数，如bindcode，传默认值，如0或空字符串。因为有些参数并不是必须的。根据新的事实澄清，改动代码实现，有不清楚的问我”。本轮授权范围为 RF-0019 扫描识别与 RF-0020 配网，不构成固件/云端接受任意默认值的实测结论。

- Q1 更新：`bindCode` 业务取不到时发送协议类型相符的空字符串；不因缺码在 App 本地报添加失败。其他未取得的**可选业务字段**同理采用协议允许的空值；SSID、密码、已确认身份和四个服务 URL 仍按来源要求校验。
- Q4 更新：广播 Service UUID `0x0922` 进入旧版 AES-CBC/JSON 配网，`0x0822` 进入新版 AES-CTR/逐包 ACK 配网；广播标识与厂商数据不一致或缺失时不猜测路线。
- Q2 用户回答：“可以，MAC 唯一匹配才算成功”。无码后轮询当前账号 HOME-01，只在 MAC 匹配唯一设备 ID 且角色有效时确认绑定；无MAC或歧义保持待确认，不走空码PAIR-05。
- Q3 用户回答：“②先加密”，确认0922先发送明文`encrypt_note`，随后发送加密的`cipher`。0822问题用户反馈“0x87不是app要发的！是固件对0x07的回复吧”；该说法正确，但0x87与问题中的0x8F是两个不同命令。已解释0x8F是App对0x0F的确认，并再次询问DATA，仍待回答。

下一轮用户一度回答“没有8f的cmd，应该是它新版最小联调序列这里写错了”；同时确认固件`user_token`“是，直接用accessToken”。其后用户明确更正：“我理解错了，`0x8F set_chiper_factory_reply` 为 APP 对模组 `0x0F` 的确认，CRC 对即 `get_info_flag++`。从这句话看，固件那边是要app写这个的，固件只验证crc，故内容它不关心，用零长度data可以”。最终决策以这条更正为准：App校验0x0F后发送DATA为空的0x8F，再依序发送0x01～0x0A。App登录accessToken作为本次设备user_token，不写入配置文件或日志。空DATA的固件接受仍需实机验证。

用户多轮回答已经明确广播选路、0922加密先后、可选参数占位、无码HOME-01唯一MAC确认、设备Token映射与0822发送空DATA的0x8F。共同理解的剩余限制为该DATA的真实固件接受、0922真实固件收发和HOME-01真实MAC可用性，均保持draft及实机待验收。

上述两条用户决策已足以更新对应的发现/路由与本地参数规则；未确定的协议报文和无码云端确认保持 draft/待确认，不伪造批准或真实验收。
