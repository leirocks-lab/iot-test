# CHG-20261023-001 需求问询：0822 回包 CRC

日期：2026-10-23。范围为 RF-0020 的真实 0822 收包校验及同一配网会话内后续写入，依据范围表 REQ-053/054 与既有 AC-018/019。

## 已核实事实与决策树

1. 前置事实：用户实机提交 Wi-Fi 密码后报“0822通知帧LEN或CRC校验失败”。2026-10-22 受限联调中，首条 `0x80 + ok`、第二条 `0x0F` 工厂挑战均可用广播 MAC + 型号前四字符的密钥和全零 IV 解密，帧头/LEN 及工厂摘要正确。两条固件回包 CRC 分别为 `0x48`、`0x8F`；对其明文使用非反射多项式 `0x31`、初值 `0x00`、无最终异或，两条均匹配。当前 App 使用反射多项式 `0x8C`，两条均不匹配。来源：[CHG-20261022-003 实机证据](<../变更-20261022-003/任务清单.md>)、[固件联调说明](<../../../docs/RowanBleNetconfTest/README_BLE配网.md>)及 Android 日志。
2. 用户前轮回答“暂无源码，按受限试验继续”；本轮反馈相同失败。未取得设备端 `crc_table` 或 `lf_crc8_check()` 源码，不能把推算结果冒充源码契约。
3. 初步修复：0822 模组到 App 的通知严格使用两条实机向量支持的非反射 CRC；首条握手与工厂确认的现有编码保持不变。后续第 6 项新增证据表明参数帧需另行修正，因此不能把全部出站命令概括为同一算法。各命令不同时宽松接受两种 CRC；其他协议和环境不扩散。
4. 本轮后续实机诊断新增事实：首条事务已完成后，原生 BLE 通道的连接期 `AbortSignal` 已按预算正常结束，但复用连接发送下一条时仍检查该旧信号，导致 `蓝牙连接已停止`。诊断同时显示 `closed=false`、新写入信号未取消、GATT 发现成功。修复选择：连接期信号只约束建立连接，已建立通道的后续写入只看通道关闭状态及该次写入信号。此为既有逐项发送行为的缺陷修复，无新增业务选择。
5. 再次实机复测已越过首条 0822 回包和后续写入，固件返回拒绝命令；当前排队应答路径仅显示“设备拒绝配网参数”，遗漏实际命令码。按既有失败可观察要求，排队与等待中的拒绝均展示同一固件十六进制命令码，不推断字段含义。
6. 2026-10-23 16:05 实机串口明确记录 `set_ssid crc8 check fail!`，App 同时收到 `0x71`；仓库烧录镜像中可定位到完整的非反射多项式 `0x31` CRC 表（偏移 825172），反射 `0x8C` 表未定位到。首条握手及 `0x8F` 已走过，当前保留其发包方式；对 `0x01～0x0A` 参数帧按非反射 `0x31` 进行受限实机验证。该推断尚需逐项 ACK 证明，不能把二进制表存在等同于所有命令的确认契约。
7. 2026-10-23 16:15，参数 CRC 修正后，实机收到 CRC 正确的 `0x81` ACK，但 DATA 长度为零；App 预期回显 12 字节 SSID，故报“0822 Wi-Fi 参数回显不一致”。联调 README §6.2 写 `0x81+ssid回显`，与本机观测冲突。该现象不是用户可决策的业务选择，而是实际设备 ACK 差异。当前仅让 `0x81/0x82` 的空 DATA 按命令 ACK 接受；若非空，则继续严格比较原值。后续 `0x82` 及其他参数仍需实机验证，不推断其 DATA 格式。
8. 2026-10-23 16:23，空 DATA ACK 修复后，App 已越过 Wi-Fi 两参数，设备报 `0x14`。联调 README §6.2 将 `0x14` 列为绑定码空值错误。用户在 2026-10-22 原话授权“业务无法明确拿到的参数，如bindcode，传默认值，如0或空字符串”；前轮选择的空字符串已被实机否定，故本轮在该授权范围内改为 UTF-8 字符串 `"0"`，不将占位码误认为真实绑定码。云端是否接受该占位码仍待设备实测。
9. 2026-10-23 16:28，使用占位绑定码后 App 十项参数 ACK 均完成，但 120 秒内没有设备阶段，报“设备配网状态等待超时”。文档 §6.2/6.4 规定无 ACK 的 `0x8F` 只有 CRC 对才使 `get_info_flag++`，计满 12 项才触发 Wi-Fi。当前 `0x8F` CRC 为反射算法 `0xCD`；同一明文按模组非反射 `0x31` 算得 `0x54`。之前“后续参数可写”并不能证明 `0x8F` 已计数。按用户已授权的受限试验，仅调整 `0x8F` CRC 并以下一轮真实阶段及串口验证，不改已有 ACK 的 `0x00`。
10. 2026-10-23 16:40 与 16:47 两轮实机：`0x8F` 改用 `0x54` 后，十项 ACK 完成，模组报告 Wi-Fi `CONNECTING/CONNECTTED`，App 通知进入 `A1 → A0 → C1`；其后 120 秒内无下一阶段，设备重新报 `AP_UP`。PAIR-04 四地址均是 `http://47.107.80.36`；开发机可连该主机 80，不能连 443。仓库测试镜像存在 HTTPS 客户端与 `https://` 字符串，未见 `http://` 字面量，但没有当前固件 HTTP 请求/响应或源码，故“HTTP 与固件证书流程不兼容”仍为待验证推断。首页未见该设备，不能判云端绑定成功。下一步需要设备端证书请求日志及云端对应接口可达的地址/响应，不能仅由 App 继续重发 Wi-Fi 参数消除该缺口。

## 共同理解与限制

用户此前明确要求按新事实修改代码实现，本轮要求处理实机失败；本变更按上述证据修复已有配网行为，不增加新业务选择。十参数 ACK 与 Wi-Fi 连接已由实机验证，证书阶段以后的设备/云接口结果、固件源码与完整绑定仍待确认；规范保持 draft，不据此宣称成功配网。
