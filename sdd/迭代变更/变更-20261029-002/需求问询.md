# CHG-20261029-002 需求问询

日期：2026-10-29。范围：RF-0017 的产品二维码格式及扫码后的添加路径；设备分享二维码、PAIR-06 服务端契约不在本轮自行定义范围内。

## 用户指令

用户原话：“目前甲方没有给出产品二维码，我决定自己先定个简单的，能支撑业务流程即可。”此指令授权在既有产品二维码业务范围内提出自定义格式，不等于对具体格式、分享码协议或逐项建议的批量确认。

## 已核实事实与来源

- Excel `APP功能清单` 第 38～42 行对应 REQ-037～041，包含相机扫码、相册识别、二维码解析、无效码及扫码绑定；主归属为 RF-0017。
- `src/screens/Scan.tsx` 的相机和相册使用同一 `QrScanFlow.read`；产品码确认后当前路由直接进入 `/add-provision`。
- `src/services/onboarding.ts` 的配网要求已选蓝牙设备候选和产品。只有产品 ID 的码不能直接完成配网。
- `src/services/runtime.ts` 通过 `contracts.qr` 注入正式解析器；现有 `src/config/deployment-integrations.ts` 未提供该解析器，所以真实扫码会提示协议未配置。

Q5（已回答）：建议二维码字段随设备侧契约使用小写 `productid`，值为 `LF-WM05`；App 先查 PAIR-01 产品目录，要求该 `productid` 只对应一个产品，再以其 `id=prd_100` 查 PAIR-02 并进入原蓝牙流程。理由：避免把固件 `productid` 错传给按云端 `id` 路由的 PAIR-02，也防止同一设备侧标识匹配多个产品时误选。用户实际选择：“确认小写 productid 并映射（推荐）”。

Q6（已回答）：展示修订后的最终业务决定和残余技术限制，取得共同理解确认。用户实际选择：“确认并修正（推荐）”。

修订后的最终共同理解：静态产品码仍为 JSON `type="rowan.product"`、`v=1`，但业务字段改为小写 `productid`，值取设备侧 `LF-WM05`。App 先经 PAIR-01 产品目录按 `productid` 查找唯一产品，取得云端 `id=prd_100` 后用该 `id` 调 PAIR-02；核验后进入按产品筛选的蓝牙发现、真实设备选择和原配网流程。未找到或匹配多个产品均阻断，不猜测云端 ID。旧 `productID=prd_100` 二维码样例停用；分享码协议不变。当前用户提供的目录响应没有 `bluetooth`，实际配网仍需 PAIR-02 返回确认能力及真实蓝牙设备验证。用户已明确确认修正规范、代码和样例。原 Q1～Q4 历史选择保留为本轮中间决定，不再作为当前格式执行依据。
