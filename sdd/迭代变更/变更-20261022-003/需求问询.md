# CHG-20261022-003 需求问询：HTTP 配网地址联调

日期：2026-10-22。范围仅为 RF-0020 / REQ-053 的 PAIR-04 四个设备侧服务地址在开发测试环境的校验；不增加 API 或产品能力。

## 已核实事实与来源

- Android 实机调用当前 IoT API 的 PAIR-04 返回 HTTP 200、业务码 0，`certificationURL`、`activationURL`、`bindingURL`、`otaURL` 均存在，但均为 `http:`、主机 `47.107.80.36`；见 [上一轮实机阻塞记录](<../变更-20261022-002/任务清单.md>)。App 的 0922 和 0822 真实编排均在发送前要求 `https:`，因此报“配网服务地址未提供有效HTTPS地址”。
- 设备侧《WiFi模组联调 API手册 v1.0》写四个 HTTPS 地址、`https://{host}:443`；对当前 IP 直接试 HTTPS 发生 TLS 意外 EOF，不能假设替换协议前缀即可使用。
- 范围依据 REQ-053 要求配网前取得 PAIR-04 四个地址；本轮不调整四地址字段或目标功能。
- 现有业务 API 基址已在 development/preview 允许 HTTP，但设备侧四地址原先独立要求 HTTPS；两者是不同校验边界。

## 决策树与本轮问询

根：为当前联调放行 HTTP 服务地址（用户原话：“想要先改成支持http的测试下”）。

1. 环境边界（前置决策）：HTTP 仅在当前 development、在 development+preview，还是所有环境？建议仅 development，原因是本轮目的为临时实机联调，设备文档仍以 HTTPS 为正式契约。
2. 依赖于 1 的实现与验收：0922/0822 共用相同的四地址校验；四地址仍必须是无首尾空白的有效 URL、主机非空，development 可用 `http:` 或 `https:`，preview/production 只用 `https:`；不得自动改写云端地址，也不以地址放行代表设备端 HTTP 可达或配网成功。

## 用户实际回答与共同理解

- 对问题 1，用户选择：“是，仅 development 放行 HTTP（建议）”。这是用户对本轮环境边界的明确确认；问题 2 是该边界及既有双协议行为的直接技术落实，已在执行前向用户展示。
- 最终共同理解：当前 development 使用 PAIR-04 原值发给模组，允许四个有效 HTTP 地址通过本地预检查；preview/production 继续 HTTPS。只验证地址格式与环境策略，不保证设备后续能访问 HTTP 服务。
- 残余限制：设备文档仍规定 HTTPS；真实固件是否支持 HTTP、认证/激活/绑定/OTA 是否正常、账号绑定是否成功均需实机和云端证据。规范保持 draft，交付保持 in_progress。

## 实机联调衍生的 CRC 待确认分支

前置事实：2026-10-22 Redmi K30 Pro 与 0822 模组联调，首帧 21 字节、MTU 247；模组返回 7 字节、帧头和 LEN 正确的 `0x80 + ok` ACK。用广播 MAC + 型号前四字符、全零 IV 解密成功。回包 CRC 为 `0x48`，App 当前 CRC8 算出 `0x65`，CRC-8/07 算出 `0x2B`；同一反射多项式若采用初值 `0xFF`、最终异或 `0xFF`，此样本算出 `0x48`。App 随后因校验失败关闭会话，原生写入报 DeviceDisconnected (201)。单个样本不能证明全部回包的 CRC 参数，也不能据此放松生产校验。

依赖问题：是否能取得当前设备端 `crc_table` 与 `lf_crc8_check()` 源码作为权威依据？若没有，建议只在 development 以受限方式验证候选 CRC 对第二条工厂挑战是否也成立，失败即终止且不发送 Wi-Fi 凭据；得到第二条独立向量后再决定正式规则。

用户实际回答：“暂无源码，按受限试验继续”。最终共同理解：开发环境只延迟首条错误回包造成的断线，以便观察模组已计划发送的第二条工厂挑战；不接受错误 CRC、不发送后续 Wi-Fi 凭据、不改变 preview/production 处理。两条独立向量若一致，再核对固件来源并决定正式修复；此试验不代表 CRC 契约已确认。
