# CHG-20261022-003 实施计划

## 输入与边界

依据[变更提案](<变更提案.md>)与[需求问询](<需求问询.md>)，只改 RF-0020 v1.7.0 的 REQ-053/054 四地址预检查，关联 AC-007/019/024/026。当前 development 的 PAIR-04 四地址为 HTTP；设备文档正式契约仍为 HTTPS。

## 实现方案

在真实运行装配时把已校验的 App environment 传给配网协调器；两条协议共用一处四地址校验。默认及非 development 均只接受 HTTPS，development 接受 HTTP/HTTPS。所有环境保留非空、无首尾空白、有效 URL、主机存在的检查；不改写返回值，不将 token、密码、完整 URL 记录到日志。

实机发现的预提交错误显示遗漏同步修复：Wi-Fi 输入页呈现 `useAction` 的具体失败信息；继续在提交结束后清空密码，不从页面闪回推断设备已收到凭据。覆盖该预提交失败场景的 UI 测试。

## 接口与兼容

PAIR-04 接口、字段名及请求方式不变；仅 App 本地 development 预检查放宽。既有 HTTPS 地址始终可用，preview/production HTTP 仍在首个 BLE 写入前拒绝。无数据迁移；回退可恢复原来的统一 HTTPS 限制。

## 验证与交付

针对 0922/0822 测试 development HTTP 四地址可进入发送、缺失/非法地址仍拒绝、preview/production HTTP 拒绝、HTTPS 在所有环境通过。执行 typecheck、lint、相关 Vitest、`pnpm specs:index`、`pnpm specs:check`。在当前 Android/模组上重新提交，记录设备收到参数后的真实阶段；地址放行不等于配网成功。无真实验收则不标 verified/released。

对 Wi-Fi 页补充失败呈现验证：预提交错误发生时用户能看见原因、密码仍清空；不将失败误显示为绑定成功。

## 0822 CRC 受限诊断

用户于 2026-10-22 明确允许“暂无源码，按受限试验继续”。development 仅在首条 0822 ACK 解出固定 `0x80 + ok`、当前 CRC 失败且候选 CRC 匹配时，短暂保持连接以接收下一条工厂挑战；仍拒绝首条错误回包，不发送 `0x8F`、SSID 或密码。第二条只在本地检查帧头、候选 CRC 和工厂摘要，日志只记录布尔结果及 CRC 数值，不记录原始报文/凭据。超时或第二条出现后关闭会话，页面继续报失败。preview/production 维持原处理。该诊断不写入正式协议要求，只有拿到独立证据后再决定是否修正规范与正式解码器。
