## 已核实事实与来源

- 已直接核对原始 Excel `SRC-SCOPE-001` 的 `APP功能清单!A92:H96`：REQ-091/092 分别检查 MCU/Wi-Fi 新固件，REQ-093 创建任务，REQ-094 查询状态与进度，REQ-095 取消；均为 P2、负责人李。REQ-094/095 描述中的 OTA 编号与各自 API 列相反，记录为 C-001。
- Word `SRC-PRODUCT-001` §8.10 和部署只读 OpenAPI `SRC-REAL-API-001` 均将 OTA-05 定义为 GET 查询、OTA-04 定义为 DELETE 取消。此前 RF-0045 问询已采纳按 API 列与 Method/Path 执行，原 Excel 不改写。
- 部署 OTA-01/02 响应有 `hasUpdate`、`firmware`、`device`；无已发布固件或已最新时 `hasUpdate=false`、`firmware=null`。OTA-03 以 `type=mcu|wifi` 和 `firmwareID` 创建任务，成功只返回 `taskID`，不代表升级完成。其在同设备同类型非终态任务存在时复用 taskID；但已登记接口中没有按设备列举任务的能力，创建响应丢失时端上无法找到 taskID。
- 部署 OTA-05 的统一任务查询返回 `result`、`status`、0～100 的 `progress` 及时间字段，可用于 MCU/Wi-Fi；Word 旧表仅列 `result` 并以 MCU 命名，此差异记录为 C-010。部署 OTA-04 明确允许 waiting/downloading/upgrading 非终态任务请求取消，终态或竞态返回 400；取消成功无 data，仍需读回结果。
- Excel 未限定管理员角色；Word 与部署 OTA-01～05 均使用 Bearer 及“未绑定”权限，未规定仅管理员。当前 Mock `http.ts` 却用 `admin()` 拦截全部 OTA。`RowanService.preference()` 已以 `userID` 自动隔离本地偏好；当前 `Ota.tsx` 未按会话 revision 隔离内存态。
- 当前 `Ota.tsx` 仅显示简化 `result`，硬编码取消提示，任务恢复仅保存 taskID，存在在途请求、重复创建和结果未知的处理缺口；`RowanService.startOta` 的默认 401 刷新可能自动重发 PUT。UI 原图支持发现新版本、已最新、进度百分比和终态，但不构成新增功能范围。

## 决策树与分轮问询

前置事实确定本轮只涉及已有 MCU/Wi-Fi 检查、创建、查询和取消。第一轮裁定无 taskID 时的安全边界；已绑定权限与服务端取消守卫互不依赖，可在其后分别核实。上述回答共同决定本轮流程，再提交最终理解确认。

### 第一轮

❓ **Q1 — 创建结果未知**：OTA-03 超时或响应丢失且没有 taskID 时，是否保留本账号本设备“创建结果待核对”状态、不自动重发、不报成功，并阻止再次创建，待任务发现/幂等核对能力确认后恢复？

➡️ 建议采用。理由：当前端上没有可靠的按设备找回任务接口，自动重发可能重复下发升级。用户实际回答（2026-10-14）：“采用建议，未知时阻止重复创建”。

### 第二轮

❓ **Q2 — 角色权限**：是否按已部署“已绑定”权限允许当前设备的已绑定账号操作 OTA，修正 Mock 的管理员限制，真实角色权限待联调验收？

➡️ 建议采用。理由：Excel/Word/部署未规定管理员专属，Mock 不应无依据收窄。用户实际回答（2026-10-14）：“采用建议，按已绑定权限”。

### 第三轮

❓ **Q3 — 非终态取消**：是否按部署 OTA-04 的 waiting/downloading/upgrading 守卫提供取消入口；确认后请求，DELETE 成功或已终态冲突均再读 OTA-05，不把取消响应当设备回滚？

➡️ 建议采用。理由：服务端以条件更新防竞态，实际终态以查询为准；旧页面“安装开始后无法取消”与部署契约矛盾。用户实际回答（2026-10-14）：“采用建议，非终态可请求取消”。
