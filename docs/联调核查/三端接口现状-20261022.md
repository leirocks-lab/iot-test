## 联调前必须澄清的差异

1. **绑定码**：用户要求非必填；手册同时写新版 `0x04` “逐条发，缺一报错”、`0x14` 表示 bindcode null，设备绑定 POST Body 又含 `bind_code`。需确认当前板子的固件版本是否允许空值、如何参与 12 项计数，以及云端无 code 是否接受绑定。
2. **`0x8F` DATA**：新手册未给准确载荷；旧V1.1写 `ok`，新版 README 写 `0x8F+...`。当前 App 要求明确注入，不能以测试样例自动当作当前固件契约。
3. **地址与鉴权**：PAIR-04 返回的四个实际 URL、设备侧 token 格式、证书 URL 的可达性、设备 POST 实际请求/响应均需云端样例和真实日志。
4. **两种 BLE 路线**：手册称旧版供用户配网、新版供售后；当前酒柜产品同时标 B/C，App 只做新 0822。需确认此产品／本轮手机测试到底以哪种服务为准。
5. **云端就绪与状态码**：需云端提供设备侧 7 类 HTTPS 实现及 MQTT Broker 的部署证据和测试响应；当前可见代码及 OpenAPI 不足以判断实现程度。
6. **MQTT参数与下行 Topic**：本手册要求设备 KeepAlive 30秒、订阅 Shadow `update/accepted` 接收 desired；旧固件需求 V1.1 写 KeepAlive 60秒。需以当前设备实际 CONNECT/SUB 抓包及 Broker 回应定版，尤其核对 desired 是否确实发布在设备已订阅的 Topic。
